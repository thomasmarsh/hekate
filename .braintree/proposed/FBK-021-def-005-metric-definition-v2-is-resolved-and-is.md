# Feedback

Attempted: Closing slice-F finding F6 in TAS-048: make the batch-level aggregation carry the full mode and movement slices, including the event-family counts the run artifact already has.
Friction: DEF-005-metric-definition-v2 is resolved and is the authority a consumer reads for metric semantics, but it deliberately deferred the aggregation slice shape to TAS-048 (its "What v2 does not claim" section names "batch-level slices of the operational families beyond mode ... together with the event-family mode and movement slices (slice-F finding F6)"). So the implementing node had to invent the artifact vocabulary: two new slice families (Aggregation::mode_event_slices keyed by one AgentMode label, Aggregation::agent_movement_slices keyed by one movement key), the rule that a counted family a mode or movement recorded nothing for is a reported zero rather than not_observed (because the run artifact by_family set always holds all ten) while a movement bucket a run does not carry at all is not_observed, and the per-slice metric-key spelling (a mode slice names an operational metric by its leaf because the slice key already names the mode). None of that is definition-level, so a consumer comparing an aggregation written before and after this change has no versioned document to read for the new keys or for the zero-versus-unobserved rule; metric_definition_version stays 2 because no metric value changed, so the definition version cannot signal the addition either. Compounding this, the run artifact spells its two sparse slices in opposite directions: OperationalMetrics::by_mode and by_movement are subject-first (mode -> metric), while EventCounts::by_family_mode and by_family_movement are family-first (family -> mode). Transposing the wrong one silently reads every family as absent and every count as 0, which is exactly the failure I had to debug (a first implementation read by_family_mode.get(mode) and reported all-zero mode slices).
Improvement: Give the aggregation slice vocabulary a versioned home rather than leaving it to the implementing node. Concretely: (1) add an aggregation-artifact section to the metric definition (DEF-005 or a successor DEF) that names every slice family (run, mode, mode pair, movement pair, agent movement), the key space of each, and the metric-key spelling inside each, the way DEF-005 already lists formulas and source locations; (2) state the count-metric slice rule explicitly ("a family a mode or movement recorded no record of is a reported 0; a bucket the run does not carry at all is not_observed") so two implementations cannot disagree; (3) introduce an aggregation artifact format version (or extend the definition-version bump rule to cover additive output slices) so a consumer can tell an aggregation that carries the new slices from one that does not, since an additive slice does not bump metric_definition_version; (4) make the run artifact key its sparse slices in one direction (subject -> family for by_mode and by_movement as well) or state the direction at the struct field, because the two opposite directions read alike and a wrong read is silent.
