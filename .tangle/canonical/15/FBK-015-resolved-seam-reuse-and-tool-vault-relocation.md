# Feedback

## Finding 1: reuse of a resolved sibling's seam by visibility widening

Attempted: Slice C2b of TAS-040 (the `compare` command) needed the metric keys and units TAS-038 (resolved) owns in its `run_level_readings`/`movement_readings` mapping, its `Spread::of`, `sample_mean`, `sample_variance`, and its `ConfidenceInterval::of` arithmetic, so the paired interval would be the same published critical-value table under another method name rather than a second implementation.
Friction: The coordination reference says "A change that alters a landed seam another node owns, or the public schema contract, is escalated rather than authored", and requires the worker to record any primitive or seam it authors in its Result. It gives no rule for the purely internal, non-behavioral reuse path: widening a private item to `pub(crate)` inside a resolved sibling module, or adding a `pub(crate)` constructor that an existing private function delegates to. Every option was a judgment call with different bookkeeping: reuse by widening visibility (touches the resolved sibling file, but alters no artifact byte, no public API, no behavior, and duplicates nothing), duplicate the seam inside the new module (keeps the sibling untouched, but creates two spellings of the metric-key/unit table that can drift), or escalate and stall a session on a decision that changes no observable behavior. Nothing in the skill says whether a non-public visibility widening counts as "altering a landed seam", who owns a resolved node's `context_rev` when only visibility changed, or whether the resolved owner node should be edited to record it (the skill forbids editing unrelated nodes as bookkeeping, while the coordination reference asks the worker to record the authored primitive).
Improvement: Extend the coordination reference beside the existing additive-field paragraph with an explicit reuse rule, e.g.: "An internal, non-behavioral reuse change in a resolved node's module — widening an item to `pub(crate)`, or adding a `pub(crate)` helper that an existing private item delegates to — is authored by the assigned worker without escalation when it changes no artifact byte, no public API, and no behavior. The worker records the widened items, the reason (one spelling instead of two), and the resolved owner in its own Result; it does not edit the resolved node and does not bump its `context_rev`, because no consumer assumption changes. Duplicating the seam inside the new module is preferred over escalating when the reused spelling would otherwise be copied." State the boundary in one sentence: visibility and `pub(crate)` factoring are not "seam alterations" unless a consumer outside the crate or an artifact shape changes.

## Finding 2: `tangle feedback record` relocated the tracked vault

Attempted: `tangle feedback record --route 'Area [[IDX-002-tangle-feedback]]' …` from the repository root, per AGENTS.md, on a clean worktree whose vault is the tracked `nodes/` directory (`git ls-files nodes` = 71 files).
Friction: The command reported success and wrote `path: "/Users/thomasmarsh/git/hekate/.tangle/proposed/FBK-015-…md"`, not the `nodes/proposed/FBK-<n>-<slug>.md` that AGENTS.md documents. Checking the worktree afterwards, the entire tracked `nodes/` directory had been moved into an untracked `.tangle/` directory: `git status` showed 71 deletions of vault files and `?? .tangle/`, so the next commit would have deleted the whole work ledger from the repository. The vault's file set and byte content were otherwise intact (`.tangle/` held exactly the HEAD `nodes/` tree plus the new FBK-015 file, with no missing or extra files), so the state was recoverable with `mv .tangle/{index-map.md,active,blocked,proposed,resolved} nodes/` and `rmdir .tangle`; `tangle check nodes` then reported the graph intact (71 nodes) and did not repeat the move. `tangle check nodes`, `hash`, and `claim` never showed this behavior in the same session, and the FBK's own `tangle_revision` moved from `0.5.0+g7b95875` (FBK-014) to `0.6.0+g4c6cafb` (FBK-015), so the relocation is consistent with a 0.6.0 change of the default vault path (the command help says `--nodes` "vault directory; defaults to ./.tangle") that migrates a `nodes/` vault on the feedback path only. Nothing in the invocation, the output, or the skill said a vault migration was happening, and a silent move of tracked files is indistinguishable from data loss until the diff is read.
Improvement: Never relocate or rename a vault's status directories implicitly. If 0.6.0's vault directory must change, make the migration explicit and reversible: accept `--nodes <DIR>` (or detect the vault as the directory holding `index-map.md` with a status subdirectory, as the skill defines the root) instead of defaulting to a literal `./.tangle`, refuse to write when the resolved vault directory differs from the one containing the tracked Markdown, and print a one-line notice naming both paths and the move when a migration does occur. A feedback command must not be able to delete a work ledger from a clean worktree; let a migration be a separate, announced command (for example `tangle migrate vault --from nodes --to .tangle`) that the operator runs and reviews in the same commit. Report the written path relative to the vault root the command actually resolved, so `path:` naming a directory outside the documented vault is visible as the failure it is.

## Recurrence note

The `git mv` staging trap recorded in [[FBK-013-i-edited-nodes-proposed-tas-038-md-adding-result]] recurred: after `git mv nodes/active/… nodes/resolved/…` followed by editing the destination, `git add nodes/resolved/… nodes/active/…` failed on the now-absent source pathspec and silently staged nothing (the error was hidden by a redirect), so the resolution commit contained only the rename and required `git commit --amend`. Staging the destination path alone, or moving the node last, avoids it; the finding already stands and needs no new node.
